# Attachments — format and contract

This is the published format: an attachment can be produced against it by any tool, without
knowing anything else about gmlw. The commands are in [CLI.md](CLI.md#attachment).

## 1. What an attachment is

An **attachment** is a block of specification added to a session's startup context, after
gmlw's own preparation (profile, rules, environment, role, persona). Its main file may
point to other files of the attachment, so the session reads them when it needs them
instead of carrying all of them from the start.

gmlw does not care what an attachment is about or how it was made. It may be written by
hand in any editor, generated by a tool, or produced in a gmlw session. A workflow is one
kind of attachment; an attachment is not a workflow, and gmlw has no notion of workflow.

An attachment knows nothing about gmlw. Its files refer to each other by paths relative to
its own folder, and nothing else.

A session runs with one attachment or with none. A session without one is an ordinary
session: nothing else about it changes.

| gmlw does | gmlw does not |
|---|---|
| import, store, export, list and delete attachments | create or modify them |
| check that a stored version is unchanged before using it | read or interpret any file other than the manifest and the main file |
| deliver the main file and let the session reach the rest | load the other files into the context |
| record which attachment and version each session ran | run the attachment's scripts |

## 2. The format

An attachment is a **zip**. Its file name does not matter. At its root is a
`manifest.yaml`:

```yaml
name: workflow-creator
description: Create a workflow, step by step.
version: 1.0.0
main_md_file: main.md
```

| Key | Required | Rule |
|---|---|---|
| `name` | yes | `^[a-z0-9][a-z0-9-]*$` |
| `description` | no | One line, shown in listings. |
| `version` | yes | Exactly `MAJOR.MINOR.PATCH`, three numbers without leading zeros: `1.0.0`, `2.1.0`, `2.10.3`. Refused: `2`, `2.1`, `v1.0.0`, `1.0.0-beta`, `1.02.0`. |
| `main_md_file` | yes | The file delivered into the context, relative to the zip's root. It must exist in the zip. |

Everything else in the zip is the attachment's own business, in any layout. gmlw never
reads it.

The author sets the version. Versions are compared number by number, left to right, so
`2.10.0` is above `2.9.0`.

## 3. Import

Import is the only way an attachment enters gmlw:

1. unzip into a temporary folder, refusing paths that escape it (`..`, absolute paths,
   links);
2. read `manifest.yaml` and check it against §2;
3. if `<name>` already has `<version>`, stop: a stored version is immutable, so new content
   needs a new version;
4. create `~/.gmlw/attachments/<name>/<version>/` and move the files into it, read-only;
5. hash the folder and record the hash in the ledger.

A version does not have to be the highest: importing `2.1.0` after `3.0.0` is a patch of
an older line, and is accepted.

## 4. The store, and immutability

```
~/.gmlw/attachments/<name>/<version>/
```

Every imported version is kept until the user deletes it.

The hash is a SHA-256 over the version's folder: every relative path and its bytes, in
sorted order. Before attaching a version, gmlw computes it again and compares it with the
ledger. If anything was added, removed or changed, the version is **invalid**: gmlw refuses
to attach it and says so. An invalid version can only be deleted and imported again.

The hash proves the folder is unchanged since its import. It does not say where the
attachment came from or whether its content is safe, and gmlw records no origin: the user
imported it, and that is the trust.

## 5. Operations

| Operation | Where | What it does |
|---|---|---|
| import | menu, `gmlw attachment import <zip>` | §3 |
| export | menu, `gmlw attachment export <name> [<version>]` | writes the version back as a zip, ready to be imported elsewhere |
| list | menu, `gmlw attachment list` | names, versions, descriptions, and any invalid version |
| delete | menu, `gmlw attachment delete <name> <version>` | removes one version |
| modify | menu only | a shortcut, below |

**Choosing** an attachment and its version happens only when setting up a session:
`gmlw start <job> --attach <name>[@<version>]`, or Job → New in the menu. The default
version is the highest one installed.

**Modify** is not a gmlw function: the user changes an attachment with whatever made it.
The menu entry only saves typing. It opens the new-job screen with the job named
`modify_<name>_v<version>`, lets the user pick an attachment to work with, and starts the
session with a message asking the client to export that version into the job's folder and
help the user change it. The result comes back through import, as a new version.

## 6. What gmlw does at session start

1. **Context.** The main file is added to the startup context after gmlw's own groups, as
   written. gmlw introduces it with a short paragraph of its own, giving the attachment's name,
   version and folder (`~/.gmlw/attachments/<name>/<version>/`, as an absolute path), and
   saying that paths in it are relative to that folder. That line is gmlw's; the
   attachment does not contain it.
2. **Access.** The session works in the job's folder; the attachment is elsewhere. gmlw
   opens the store to the session with the client's own flag, `--add-dir` on claude, codex
   and vibe. Some clients grant write access with it; the read-only files and the hash
   check (§4) still keep a stored version from changing unnoticed.
3. **Environment.** The attachment's credentials, if the user set any (below).
4. **Opening.** The session starts with a short message naming the attachment and its
   version. What the session does next is the attachment's business.
5. **Record.** The session records the attachment's name, version and hash.

A session's own output, an attachment being written included, goes to the job's folder.

**Credentials.** A secret an attachment or its scripts need is registered under the
attachment's name, `gmlw creds set <name> <ENV_VAR>`, stored in
`~/.gmlw/credentials.toml` (mode `0600`) and exported as `ENV_VAR` to a session started with
that attachment. It is not part of the attachment, so it never travels with an export. See
[SECURITY.md](../SECURITY.md).

**Scripts.** An attachment may carry scripts; its text tells the session when to run them,
by their path inside the attachment. gmlw never runs them itself.

## 7. The provided attachment

gmlw ships one attachment, `workflow-creator`. It enters the store through the same import
as any other: whenever gmlw starts, a provided version the store does not hold yet is zipped
and imported, so an upgrade that carries a new version adds it beside the old ones. gmlw has
no other path for its own content. Deleting a provided version brings it back at the next
start; it is always there to build workflows with.

## 8. Coming from an older gmlw

Older versions had *workflows*, kept as folders under `~/.gmlw/workflows/`. On the first
command after upgrading, gmlw imports each of them once, as `<name>@1.0.0`:

- its `workflow.md` is the main file, with the old shared base (`_common/base.md`) put in
  front of it, so it behaves as it did;
- its other files come along — scripts, references, anything it reads — except authoring
  leftovers (`draft.md`, `parking-lot.md`, `*.bak*` copies), caches, and the clients'
  permission folders (`.claude/`, `.codex/`, `.cursor/`);
- its description comes from its `.about.toml`;
- its credentials keep working: they are filed under the same name.

The old folder is never written to: delete it when you no longer need it. A workflow that
wrote into its own folder while running (state, logs) cannot do so as an attachment, which
is read-only; move that data to the job's folder, for instance in a session with
`workflow-creator`, and import the result as a new version.

Sessions that ran a workflow keep showing its name, without a version. Old config keys
(`[startup.workflow]`, an interceptor bound to `workflow`) are renamed to their attachment
equivalents, with your comments kept. `gmlw workflow …`, `gmlw run` and `--workflow` are
gone: creating a workflow is a session with `workflow-creator` attached.
